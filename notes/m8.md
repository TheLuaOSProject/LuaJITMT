# M8 Notes

Weak modes and current finalizer semantics:

- Original plan state: `plan/12_implementation_plan.md` defines M8 as the
  complete weak-table and finalizer milestone: full `gc_mayclear()` parity,
  the weak resurrection-race store hook, finalizer thread/ordering,
  `ffi.gc()` interplay, keeping Lua 5.1's "no `__gc` on tables" rule, and
  `lua_close()` finalization drain.
- Current bridge state entering M8 already had GC2 weak snapshots, legacy-color
  weak clearing, P_WEAK write barriers, and finalizer sweep guards staged from
  M3/M7. This slice does not replace those bridges with the final
  scheduler-owned weak/finalizer design.
- Added `tests/t-weak-modes.lua` to cover the planned `t-weak-01..05` semantic
  surface that is deterministic today:
  weak-value, weak-key, and all-weak table modes; string keys/values not being
  weak-cleared; cycles made only of weak tables not keeping themselves alive;
  `ffi.gc()` reverse finalizer order; explicit `ffi.gc(cd, nil)` clearing;
  nested GC inside a cdata finalizer; the Lua 5.1 rule that table `__gc` does
  not run; a finalizer that spawns and joins a thread; and a bounded concurrent
  weak-value writer safety pass.
- Added `tools/ci/m8_weak.sh` as the first explicit M8 gate. It runs the Lua
  semantic test under interpreter and default JIT, runs the existing
  `t-gc2-phase` finalizer phase accounting coverage, runs the existing
  `t-gc2-traverse` weak/barrier C coverage, and runs
  `tests/t-m8-close-finalizers.c` to assert `lua_close()` drains cdata
  finalizers and chained userdata finalizers. It then rebuilds with
  `LUA_USE_ASSERT` and `LJ_GC2_PARANOIA` and reruns the focused weak/close
  gates.
- Extended the finalizer phase guard regression checks so `lj_gc2_finalizer_enter`
  records the current TG owner, peers remain blocked while the owner can finish
  nested sweep work, and `lj_gc2_finalizer_leave` clears owner state while
  advancing the leave counter exactly once. This tightens the current bridge
  accounting; it is not the final async/per-thread finalizer dispatch design.
- The original "finalizer that spawns a thread" probe initially hung because
  `threading.spawn()` waited for `mt_gc_exclusive` while the caller was already
  inside explicit full-GC finalization. `gc_call_finalizer()` now releases that
  explicit-GC exclusion only around the protected user finalizer call, then
  waits for finalizer-spawned threads to leave and reacquires exclusivity before
  the collector resumes. This is a correctness bridge for finalizer-spawn
  semantics, not the final async finalizer-thread architecture.
- Remaining from the original M8 report after this slice: make finalizer-spawn
  broadly scheduler-owned, replace the shared-VM-thread finalizer callback
  bridge with the planned dispatch path, finish scheduler ownership of
  weak/finalizer phases, and extend the paranoia oracle beyond the current
  focused weak coverage. Performance and cleanup remain deferred to M9.
