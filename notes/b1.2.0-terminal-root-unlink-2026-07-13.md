# b1.2.0 terminal root unlink progress

## Release blocker

A stopped-GC allocation workload completed its loop but deterministically
livelocked in `lua_close()` once a built-in finalizable userdata was more than
`LJ_GC2_ROOT_SCAN_LIMIT` ownership-spine nodes below the head.  The exact
pinned-CPU boundary on `7e4c2c86` was:

- 999,789 table allocations: loop and close completed;
- 999,790 table allocations: the loop completed in about 0.132 seconds, then
  close timed out;
- 999,791 table allocations: the same close timeout.

The repeated path was:

```
lua_close
  -> lj_gc2_finreg_udata_finalize(g, all=1)
  -> lj_gc_unlink_root_obj
```

The ordinary unlinker correctly restored `MEMBER` and returned `UNPROVEN`
after its bounded million-node scan.  Terminal FINREG discovery then retried
the identical finite prefix without changing it, so the runtime safety bound
became a deterministic shutdown livelock.  Profiling showed the repeated
per-node tactical SMR admission was also expensive.

## Implemented terminal protocol

Ordinary runtime unlink remains bounded and try-only.  `all=1` FINREG
discovery now selects `lj_gc_unlink_root_obj_terminal()`:

1. Try to acquire one SMR reader for the complete attempt.  An active exclusive
   reclaimer returns `UNPROVEN`; terminal discovery retries without waiting.
2. Claim the exact target membership `MEMBER -> UNLINKING` before flushing
   pending publishers, as in the runtime protocol.
3. Scan to the target or `NULL` without the runtime count cap, using
   `gc_root_link_valid_held()` and its same-arena validation cache.
4. Preserve the predecessor CAS and exact `UNLINKING -> NONE` commit.  Every
   validation/CAS loss restores `MEMBER` before releasing the reader.
5. Run allocation-free Brent cycle detection during the terminal walk.  A
   multi-node cycle restores the target claim, invokes the existing cycle
   repair under the held reader, and returns `UNPROVEN` for a later retry.

The in-pass detector is required even though the normal path calls
`lj_gc_repair_root_spine()`: the repair epoch is an optimization hint and can
legitimately be cached after an exceptional validation or CAS loss.  It must
not be the sole progress proof for an unbounded terminal traversal.

After `lj_threading_shutdown()`, secondary mutators cannot attach or grow the
spine.  Parked collector workers can only consume or rearrange the finite
existing population.  The SMR reader pins acquired arena mappings throughout
the scan, while the target root-state claim pins its allocation identity.
Consequently a successful predecessor CAS removes exactly one ownership edge;
a lost CAS safely restores the claim and retries later.

The production terminal API is deliberately separate rather than weakening
the ordinary runtime guard.  A test-only bounded entry makes the cap behavior
deterministic with a 64-node fixture: the runtime mode must return `UNPROVEN`
and preserve membership, then terminal mode must cross the same prefix, unlink
once, and permit a clean re-link.

## Validation

- `m3_gc_root_pending_race`: pass, including the 64-node bounded/terminal
  distinction and a stale-repair-epoch two-node cycle.
- `m3_gc2_worker_scheduler`: pass, including `all=1` separation with two
  parked workers.
- `m8_gc2_finreg_udata_roots`: pass.
- Real boundary rerun at 999,789, 999,790, and 999,791 allocations: all loops
  and all shutdowns completed, in 0.132--0.135 seconds for the allocation loop.
- Default and `LJ_GC2_TEST_HELPERS` builds: pass with `-Werror` fixtures.

## Remaining performance work

This fixes shutdown progress, not the separate allocation hot-path cliffs.
Two independently measured issues remain release blockers:

- selecting a bin run while an owner-private bump window is live repeatedly
  republishes and fully scrubs the shrinking suffix;
- when the bump is exhausted, an empty remote-free probe scans every owned
  arena, causing smooth quadratic growth with stopped GC.

The recommended first allocator change is to consume the already-private bump
window before consulting bins.  The remote-free scan needs a separate
allocator-level pending indication (and eventually a ready-arena worklist).
Even after those fixes, collector cadence currently leaves the representative
allocation loop well above the b1.2 per-row `3x` performance gate, so the
release is not ready.
