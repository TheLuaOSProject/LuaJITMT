# M5 notes

M5 recorder template hmask snapshots:

- Updated the table-bump recorder path for template tables so both the grown
  table and template table derive hash sizes from the acquired node header
  instead of `GCtab.hmask`. Template hash scans now walk the same node/mask
  generation they acquired.
- Extended the HREFK recorder guard to reject the old `tb->hmask` and
  `tpl->hmask` template-table spellings in addition to the constant-slot HREFK
  shape snapshot checks.

M5 x64 JIT HREF node-header hmask:

- Updated x86/x64 regular `IR_HREF` lowering so dynamic hash lookups load the
  mask from `TabNodeHdr` at `node-sizeof(TabNodeHdr)` after the generated trace
  has loaded `GCtab.node` into the destination register. The backend no longer
  emits `offsetof(GCtab, hmask)` for regular HREF hash indexing.
- This closes the regular dynamic-HREF mixed `GCtab.node`/`GCtab.hmask` reader
  for the current headered-node representation. Constant-slot HREFK guards and
  hash stores still need the original 08 section 8.8 `NHdr`/generation-aware
  trace work and the 06 section 6.3 write protocol.
- Tightened `tools/ci/m5_jit_href_node_order.sh` to require the
  `TabNodeHdr` displacement and reject `offsetof(GCtab, hmask)` in the x86
  backend.

M5 x64 table node-header hmask reads:

- Updated x86-64 read-only hash fast paths to load `GCtab.node` first and then
  load the hash mask from `TabNodeHdr` at `[node-8]`, rather than reading the
  legacy `GCtab.hmask` mirror. Covered paths are `getmetatable`'s
  `__metatable` probe, `ipairs_aux` empty-hash fallback check, `lj_vm_next`
  hash traversal, `BC_TGETS_Z`, and the hash traversal part of `BC_ITERN`.
- `BC_TSETS_Z` now also computes its string-key hash slot from the node header,
  but this remains only a crash-safety/coherent-addressing step. It does not
  implement the original 06 section 6.3 RETIRING/FORWARD/CAS write protocol,
  and hash stores still need the full `NHdr` migration/write design.
- Tightened the existing x64 guards to require the `[node-8]` header loads and
  reject the old `TAB->hmask`/`NEXT_TAB->hmask` pairs.

M5 table node-header hmask slice:

- Added a small `TabNodeHdr` immediately before every table hash `Node[]`
  allocation, while keeping `GCtab.node` pointing at `Node[0]` for existing
  VM/JIT addressing. The header carries the mask for that exact node vector, so
  C readers can derive `(node, hmask)` from one acquired publication instead of
  pairing `GCtab.node` with a separately observed `GCtab.hmask`.
- Gave the shared empty hash fallback a real header by embedding
  `global_State.nilnodehdr` immediately before `global_State.nilnode`; empty
  tables still point at `&g->nilnode`, but `lj_tab_node_hmask_acq()` is now
  valid for every published table node pointer, including the nilnode.
- Updated table allocation, resize retirement, close-time free, GC/GC2 raw
  memory marking, bytecode/serializer/parser scans, table library scans,
  `lj_tab_next()`/key-index logic, and recorder-time HREFK shape snapshots to
  use the node-bound mask when walking a hash vector. `GCtab.hmask` remains as
  a compatibility mirror for current VM/JIT offsets.
- This is a deliberate step toward the original 06 section 6.2/6.3 `NHdr`
  design, not a replacement for it. The full header-generation helper-copy
  protocol, RETIRING/FORWARD/CAS writes, and x64 VM/JIT header-mask loads still
  remain pending.
- Added `tests/t-tab-nodehdr.c` and `tools/ci/m5_tab_nodehdr.sh`; tightened the
  empty-hash, node-publish, and retire tests to assert header-mask invariants.

M5 internal tag audit:

- Tried the straightforward section 6.1 approach of moving `LJ_TNUMX` /
  `LJ_TISNUM` down to make room for `LJ_TKEYLOCK` and `LJ_TFORWARD`.
- Reverted it after stock tests showed NaN comparisons failing. On this x64
  dual-number representation, the canonical hardware NaN pattern occupies the
  `~15u` itype range, so making `LJ_TISNUM == ~15u` causes `tvisnum(0/0)` to
  fail and comparison operators raise `"attempt to compare two number values"`.
- The table sentinel representation needs a design that preserves canonical
  NaN and integer tagging. Do not blindly lower `LJ_TISNUM` for M5 tables.
