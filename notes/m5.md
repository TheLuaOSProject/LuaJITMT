# M5 notes

M5 C table value publication helpers:

- Added `lj_tab_store*()` wrappers for common C-side table slot writes. The
  helpers build a stack `TValue` and publish it through `lj_tab_storetv()`,
  which already uses `copyTVrel()` for release-store table-slot publication.
- Converted runtime/library/parser/serializer call sites that wrote directly
  through `lj_tab_set*()` results to use the wrappers or `copyTVrel()`. This
  covers nil/bool/int/intptr/string/table/thread/proto/function/udata values
  in the touched C paths, plus the serializer dictionary preparation that used
  to write raw low bits into a table slot.
- Tightened the follow-up API/table-library cases that hid the table
  destination behind a temporary pointer: direct `lua_settable()`/`lua_setfield()`
  slots initially moved to release stores and now participate in the table CAS
  retry bridge described below; `table.insert()` position shifts plus
  `table.pack()` array initialization use `lj_tab_storetv()`/`lj_tab_storenil()`.
- Recorder template-table growth markers also use `lj_tab_storetab()` and
  `lj_tab_storenil()` so temporary nil-preservation markers are published with
  the same slot-store discipline.
- FFI/clib alias setters that hide slots behind local `TValue *` variables now
  release-publish too: FFI `__newindex` uses `copyTVrel()`, callback slot
  clearing uses `lj_tab_storenil()`, and C library cache constants use
  `lj_tab_storetv()`/`lj_tab_storeint()`.
- Added `lj_tab_storenilraw()` for state-free nil release stores and routed
  `lj_tab_clear()` plus GC weak/finalizer table slot clearing through it.
- Parser constant-table slot markers keep the original compact `hi == 0`
  encoding, but now publish that marker with `const_slot_store()` instead of
  raw `o->u64` stores; string anchors use `lj_tab_storebool()`.
- Bytecode template-table loading decodes key/value constants into local
  temporaries first and release-publishes array/hash table slots with
  `lj_tab_storetv()`.
- Serializer decode outputs now release-publish through `copyTVrel()`,
  including the early nested-table root store before recursive array/hash fill.
- Snapshot unsinking now restores table-slot values into local temporaries and
  publishes them with `lj_tab_storetv()` instead of letting `snap_restoreval()`
  write directly through a `lj_tab_set()` result.
- This is still a scoped legacy-`GCtab` bridge. It does not implement the
  original 06 section 6.3 RETIRING/FORWARD/CAS write protocol, and hash-slot
  migration correctness remains on the original plan.
- Added `tools/ci/m5_tab_value_publish.sh`, wired into the M5 aggregate, to
  keep raw `lj_tab_set*()` value publication patterns from returning.

M5 x64 TSETS hash-store slow path:

- Demoted x86-64 `BC_TSETS_Z` string-key table stores to `vmeta_tsets` instead
  of walking hash chains and writing `Node.val` directly in the VM fast path.
  This covers `TSETS`, `GSET`, and the string-key fallback from `TSETV`.
- Updated the remaining x86-64 interpreter array table stores (`TSETV`,
  `TSETB`, and `TSETR`) so the fast lookup/nil-decision path still runs in the
  VM, but the final slot publication calls `lj_tab_storetv()` instead of
  emitting a raw `mov [RC], ITYPE`. The GC2 follow-up remains the table barrier
  path, preserving SSB traversal semantics for black parent tables.
- `BC_TGETS_Z` keeps the node-header hmask read path for fast string-key loads.
  Array `TSETV`/`TSETB` paths keep their previous-value snapshots.
- This is an interim step: it removes the x64 interpreter's direct legacy
  string-key hash-chain store. The generic x64 `vmeta_tset` continuation now
  calls `lj_meta_tsettv_pair()` so the returned table slot is release-stored
  from C with resolved parent context, but the C/meta table setter is still
  legacy `GCtab` code until the original 06 section 6.3 `NHdr` write protocol
  lands.
- Updated the x64 guards so TGETS still requires node-header hmask loads while
  TSETS requires the hash-store slow path and rejects the old `mov [TMPR],
  ITYPE` store; the TSET guard also rejects the old raw `mov [RC], RB`
  `vmeta_tset` slot write.

M5 x64 TSETM array-store publication:

- Added `lj_tab_storetvn()` as a batch table-slot publication helper using
  `copyTVrel()` for each copied `TValue`.
- Updated x86-64 `BC_TSETM` so constructor vararg result copies keep the
  existing fit check, `lj_tab_reasize()` retry, and table barrier behavior, but
  publish the resulting array slots through `lj_tab_storetvn()` instead of a
  raw `mov [TMPR], ITYPE` loop.
- Follow-up: the x64 `TSETM` GC2 range barrier now calls
  `lj_gc2_barrier_tvn_pair_g()` with the destination table parent, so
  generational remembered-set filtering can queue the table instead of treating
  the copied values as parentless roots.
- This covers the resize/retry window where `lj_tab_reasize()` can publish a
  replacement legacy array before `BC_TSETM` retries and fills the slots. The
  original 06 section 6.3 `AHdr` RETIRING/FORWARD/CAS migration protocol and
  the original 07 store-barrier macro still remain the final target.

M5 JIT table-store NYI guard:

- Updated indexed-store recording so hash-based table stores (`HSTORE` paths)
  and array-based table stores (`ASTORE` paths) stop recording with the normal
  NYI-bytecode trace error before legacy direct slot-store IR is emitted.
- This is a conservative interim step for the current legacy `GCtab` runtime.
  It prevents generated traces from performing unsynchronized table-slot writes
  while the original 06 section 6.3 `NHdr`/`AHdr` RETIRING/FORWARD/CAS write
  protocol and the original 08 section 8.8 traced-store barrier/write protocol
  are still pending. The original report intended traced array stores to keep
  barrier coverage; the current M5 bridge deliberately demotes them until the
  trace codegen side can publish through the final protocol instead of raw
  stores.
- Added `tools/ci/m5_jit_hash_store_nyi.sh`, wired into the M5 aggregate, to
  assert that hot string-key and array table stores both remain interpreted.
- Updated the GC2 traverse scaffold's table-store JIT barrier check to assert
  the same interim no-trace behavior while still validating that the
  interpreter fallback enqueues the table barrier during marking. Traced
  upvalue barriers remain covered separately.
- A later M6 slice retargeted `tools/ci/m5_jit_hash_store_nyi.sh` to the current
  boundary: existing non-nil hash/array overwrites may trace through the helper
  bridge, while new-key and nil-slot stores still stay NYI. The GC2 traversal
  scaffold's non-weak JIT table-store case was retargeted the same way, while
  a later M8/M6 helper split retargeted weak table stores to trace through the
  P_WEAK-aware hash/array helpers too.

M5 table resize off-table hash rebuild:

- Updated `lj_tab_resize()` so a non-empty replacement hash vector is allocated
  and rebuilt off-table before `GCtab.node` is release-published. Old hash
  entries are copied from acquired key/value snapshots; entries that belong in
  the final array size are routed to the array, and the remaining pairs are
  inserted into the unpublished replacement hash.
- Array-tail values that leave the array during shrink are inserted into the
  unpublished replacement hash before the smaller `asize` is published. If an
  explicit resize asks for too small a hash part, `hbits` is raised from the
  counted live hash payload needed after array routing.
- Old hash-vector retirement is armed only after the rebuilt vector is
  published. This removes the previous window where readers could acquire a new
  empty or partially rebuilt hash vector while old pairs or array-tail values
  were still being reinserted.
- This is still an intermediate legacy-`GCtab` bridge, not the original 06
  section 6.3.5 cooperative `AHdr`/`NHdr` resize protocol. The original target
  remains RETIRING/FORWARD/CAS migration with helper copying; the current slice
  still uses legacy `GCtab` fields and non-cooperative one-thread copying.
- Extended the table publication/retirement gates to require rebuild-before-
  publish ordering, to cover a hash-resident integer key moving into the array
  part during resize, and to cover array-tail keys moving into the hash part on
  shrink.

M5 table rehash/new-key release publication:

- Added `tab_storekeyrel()` so hash keys are canonicalized for `-0` before the
  key slot is release-published, instead of release-storing the key and then
  patching `key.u64` directly.
- Converted resize/rehash value moves from old hash and array-tail storage to
  `copyTVrel()`. Some destinations are unpublished rebuild storage, but this
  keeps the current legacy-`GCtab` bridge uniform for slots that can become
  visible through array-size or node publication after the rebuild.
- This does not replace the original 06 section 6.3 RETIRING/FORWARD/CAS
  helper-copy resize protocol; it narrows the remaining raw-store surface while
  that protocol is still pending.

M5 x64 JIT HREFK node-header bounds:

- Added a runtime HREFK slot bounds guard in x86/x64 lowering: generated code
  now checks the recorded constant slot index against `TabNodeHdr.hmask` before
  loading `node[slot].key`. This prevents a trace from indexing past a newer,
  smaller node vector if the legacy `GCtab.hmask` mirror is stale around a
  resize publication.
- The existing HREFK key guard still verifies slot identity after the bounds
  check. Hash stores and the final generation-aware HREFK guard model remain
  part of the original 06/08 `NHdr` write/trace plan.
- Extended `tools/ci/m5_jit_hrefk_record_snapshot.sh` to require the codegen
  bounds guard in addition to recorder-time node/header snapshots.

M5 internal tag audit:

- Tried the straightforward section 6.1 approach of moving `LJ_TNUMX` /
  `LJ_TISNUM` down to make room for `LJ_TKEYLOCK` and `LJ_TFORWARD`.
- Reverted it after stock tests showed NaN comparisons failing. On this x64
  dual-number representation, the canonical hardware NaN pattern occupies the
  `~15u` itype range, so making `LJ_TISNUM == ~15u` causes `tvisnum(0/0)` to
  fail and comparison operators raise `"attempt to compare two number values"`.
- The table sentinel representation needs a design that preserves canonical
  NaN and integer tagging. Do not blindly lower `LJ_TISNUM` for M5 tables.
