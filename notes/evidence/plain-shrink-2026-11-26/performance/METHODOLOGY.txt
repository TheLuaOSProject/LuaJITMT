Small PLAIN shrink stability and performance controls

Baseline is the immutable GCC static build of commit 78f117627cdecbe83600d9e1d39c0b0f923459c1. Candidate is the final header-fixed GCC static snapshot in /tmp/lj-plain-shrink-final-20261126-lxy_jr_l/gcc. Complete source/build manifests, library/executable hashes and the exact two-file runtime patch are retained. Harnesses compile separately against each frozen tree with GCC -O2, standard C assertions enabled, and the release library.

Witness: a registered scratch allocator belongs to a real Lua universe. A 4096-byte allocation is retained by a genuine full-span GC2 storage lease while direct realloc shrinks it to 17 bytes. The original bytes and an adjacent guard are checked before releasing the lease. A second mode first fills the current bump and then refuses mmap/mmap64 through the linker wrapper. Baseline exits 1 because the desired in-place, infallible shrink contract is violated; candidate exits 0. The initial mmap-only wrapper did not intercept these libraries' mmap64 import. Those original files/results are preserved under initial-mmap-seam and are explicitly not an OOM proof. Final witness wraps both symbols and verifies actual rejection.

Ordinary alloc/free timing: one private allocator per process, one object size (64, 256 or 4096 bytes), 5000 warmup cycles and 500000 measured allocate/touch/free cycles. Five fresh paired processes per size alternate baseline/candidate order. Timing uses CLOCK_PROCESS_CPUTIME_ID and also records monotonic wall time. Processes run sequentially on CPU 8 while root validation uses other CPUs. Native mapping/bin behavior remains part of the workload; these are allocator controls, not application or stock-LuaJIT throughput measurements.

Retention timing/census: allocate N objects of S bytes, touch every byte, shrink every object to 16 bytes, then allocate N*(S/1024-1) objects of 1024 bytes. Validate all live payload sentinels, then free the shrunk originals with logical osize 16 and free all refill objects. Sizes/counts are S=4096 with N=256/2048/8192 and S=16384 with N=64/512/2048. Three alternating paired processes per configuration give 36 runs. Each phase reports logical payload bytes, bitmap-derived physically allocated bytes, block starts, owned arenas, owner-private bin capacity, active bump remainder and process CPU/wall work time. The external controller samples /proc RSS, VmSize, VmHWM and OS thread count before acknowledging each phase. Census work and controller pauses are excluded from phase work timing.

The physical allocation census walks structural block/mark boundaries and uses the current owner bump to bound its last allocation. The synthetic allocator is quiescent and single-owned; this census must not be copied into an unsynchronized concurrent arena walker. Physical allocated bytes describe reserved allocation extents; mapped RSS additionally includes free capacity, arena headers and native runtime memory.

A post-free capacity discrepancy in both variants justified four separate maximum-size attribution controls. retention-rebuild.c repeats the workload then invokes the existing owner-only plain-bin rebuild and reports again. These runs use CPU 0 and do not contribute to paired timing statistics. They distinguish lost bin discovery from still-allocated extents. The original 66 timing workloads/results remain unchanged.

All runs have bounded input counts and a 60-second process timeout. Every raw sample, initial seam mistake and timing variation is retained. There is no result filtering. Huge shrink semantics, concurrent performance, release readiness and Windows/macOS validation are outside this experiment.
