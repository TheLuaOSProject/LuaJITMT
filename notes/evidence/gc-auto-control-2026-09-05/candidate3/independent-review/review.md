The unmodified spawn-live fixture requires a child spawned by a finalizer to observe the logically enabled collector. Candidate2 failed three of six new runs, while other schedules sampled after callback cleanup and passed. The separate production diagnostic makes the overlap deterministic: the callback waits for the child's sample, then returns before the second sample. Candidate2 reports stopped during the callback and running afterward; the prior control reports running in both child samples. These are real versioned outcomes in /tmp/lj-gc-auto-control-20260905-qs673ryl/HANDOFF.md, not candidate3 tests.

The selected public contract is now explicit: ISRUNNING reports whether automatic collection is logically enabled by public STOP/RESTART. It does not report a transient callback-admission veto, current phase, or whether a worker happens to be executing. This is consistent across a callback, an existing peer and a newly attached child. STOP reports false inside and outside callbacks. RESTART, including the existing nonthrowing full-collect API return behavior, reports true even if the callback's internal pause still suppresses automatic admission. This deliberately changes the earlier sole-main callback threshold-based false result too; it is not an exact upstream callback compatibility claim.

The Lua 5.2 manual describes isrunning as whether the collector is not stopped: https://www.lua.org/manual/5.2/manual.html#pdf-collectgarbage . Its actual GCTM implementation temporarily clears gcrunning and restores it around callbacks: https://www.lua.org/source/5.2/lgc.c.html . Neither source defines this fork's shared-heap threading extension. The decision is grounded in the existing fork fixture and a consistent public control setting, while preserving the temporary internal veto independently.

lj_gc_auto_enabled acquire-loads the same auto_flags byte and tests only STOPPED. LUA_GCISRUNNING is its only new caller. lj_gc_auto_running retains flags == 0 and is explicitly documented as the automatic-admission predicate. The four other modified source files are byte-identical to candidate2. Initialization, STOP/RESTART atomic bit operations, operation-selected API updates, first/last attachment independence, callback PAUSE ownership, protected error cleanup, automatic request creation, actual driver checks and x64 pending-request admission all retain the preceding proof. The query creates no scheduling side effect and cannot admit work or remove FINPAUSE.

The full source delta was reread. Public STOP still sets only STOPPED before pacing; RESTART publishes pacing then clears only STOPPED. Numeric threshold MAX is not interpreted as STOP. Nested callback scopes keep the physical finalizer owner, and only the outer pause scope clears FINPAUSE after restoring hooks, current state and thresholds. Callback/peer STOP survives cleanup. Preexisting full-collect finalizer deferral and explicit STEP behavior remain. The new query is observational only, so it does not grant those explicit paths additional authority.

Validation must keep the original spawn-live fixture unchanged, use a new clearly versioned deterministic enabled-query oracle, and test both solo and peer callback queries with real STOP/RESTART, nesting, errors and post-unwind state. Rerun the exact first/last attachment and numeric-MAX controls and relevant ordinary/JIT/FFI behavior. Preserve candidate2's failures and old oracles. Any expected worker-two SWEEP incompletion, unrelated helper assertion or construction timeout must remain classified separately; no absence of sanitizer reports may turn a failed process into a passing gate. The driver remains synchronous, concurrent string body reclamation remains open, and neither this control change nor this review establishes release or full lockless completion.
