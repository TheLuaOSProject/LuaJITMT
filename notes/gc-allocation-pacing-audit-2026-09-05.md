Read-only allocation-trigger/pacing audit, 2026-09-05

Recommendation: keep production's 384 KiB cap and its existing active progress cadence unchanged in the current Linux runtime. The cap overcharges the pending-root bridge on rootless closure workloads, but the collector still must reclaim the allocated bodies. The next useful experiment is a bounded, isolated 384 versus 512 KiB idle-trigger comparison with the original hard-assist schedule held fixed. A successful throughput row alone is insufficient: automatic memory/arena bounds, actual pending-flush work, recovery completion and native exit progress must remain bounded. The historical reason and the present coupling

- 530fc547 (July 4) introduced the cap with the current comment: fresh per-TG ownership chains would otherwise grow with the pause-derived live-heap trigger. It initially equalled the then-256-KiB minimum. 81a84fba (July 12) changed it from the then-32-KiB minimum to twelve 32-KiB accounting flushes. The July 12 composed-closure note reports that 512 KiB or more caused a roughly 1.7 us/op nonlinear quarantine regression in the former two-pending-entry-per-iteration ownership model. That is historical throughput evidence, not a current memory-safety proof or an assertion that 393216 is an intrinsic protocol boundary.
- src/lj_gc2.h:241-253 defines accounting flush 32768, active automatic threshold quantum 4096, hard-check batch 524288, and cap 393216. src/lj_gc2.c:3337 computes max(legacy estimate or logical accounted total, arena live estimate) * pause/100, clamps to [32768,393216], and publishes hard=2*trigger. On a cap-saturated heap the hard threshold is 786432. The input is not solely the arena live-cell estimate: fallback total also counts other still-accounted runtime memory.
- All successful allocated bytes charge the same pacing counter. src/lj_gc2.c:2815 flushes per-TG local_total to alloc_total_bytes and alloc_since_trigger; :3237 flushes at 32 KiB; :3227 requests a cycle only from IDLE when global flushed allocation exceeds trigger; :2860 uses an exact cycle_leader CAS and republishes the legacy total threshold. The legacy total>=threshold path can start a cycle even at equality before a batch flush. src/lj_gc2.c:3370 publishes total+(trigger-since), clamped for saturation.
- At MARK start src/lj_gc2.c:3391/:4244 flushes registered TG counters and xchg-resets since, retaining all earlier bytes in cycle_alloc_bytes. This is start-to-start allocation debt, not bytes strictly allocated while IDLE: allocation during MARK/WEAK/SWEEP contributes to whether a new cycle is already due after close. src/lj_gc2.c:6531 and :6677 recalculate pacing after normal/forced close. Enlarging the cap can alter this whole phase mix and the amount of quarantined capacity before the next cycle.
- src/lj_gc2.c:3251 performs hard assists at allocation-accounting checkpoints. src/lj_gc.c:4123/4328 and :4350 close cooperative MARK or SWEEP native entry at the hard cadence; SWEEP assist itself intentionally does no reclaim work, so the native exit hands progress to interpreter-owned work. src/lj_gc2.c:3310 advances the next hard checkpoint by 512 KiB after current debt is above hard. A one-line cap increase also delays initial active hard checks and is therefore a confounded experiment.
- src/lj_gc.c:4144 uses at most 64 automatic state-machine steps, with a separate aggregate 64-arena SWEEP completion bound; :4194 republishes a 4096-byte active threshold (or leaves it immediately due for a bounded MARK dispatch opportunity). src/lj_gc2.c:14975 allows hard assist only in MARK/WEAK, owns the worker token and consumes limited grey/SSB/recovery work. Keep all of these paths unchanged in a cap-only investigation. Whole-table traversal is still charged as object work, so a nominal small worker count is not a slot/byte latency bound.

Pending ownership is not semantic liveness and is not quantitatively bounded

- Generic constructors hold CONSTRUCT/LINKING before publishing a pending head, then commit LIVE/MEMBER (src/lj_gc.c:663, :748, :5305). A pending chain records physical sweep/destructor ownership; ordinary stack/table/closure edges determine liveness. src/lj_gc.c:4538 explicitly documents that distinction for closing upvalues, which can publish old objects without new allocation.
- src/lj_gc.c:5204 first uses a Boolean nonempty hint (with main/current-TG fallback), tries one SMR read, then clears the hint and exchange-detaches all registered TG pending and after-main heads. Admission loss leaves all chains and the hint untouched for a future flush. src/lj_tg.h:1079 publishes hints around the empty-to-nonempty head transition; this is not a pending-work count or proof of no concurrent publisher.
- A detached suffix has no budgeted cursor: src/lj_gc.c:5034 validates the complete chain and finds its tail; :5110 checks overlap while linking; :5259 can then run the dirty-epoch root-spine repair (:974). Repair is cached when no publication changed its epoch, but a required pass is proportional to the existing spine as well as fresh work. There is no prefix quota in the pending flusher. The :3356 comment's non-blocking root-work statement is therefore a heuristic workload claim, not a demonstrated maximum number of steps.
- The allocation cap is not a mathematical pending-chain bound: stop suppresses automatic cycle requests; a large individual allocation and per-TG unflushed batches overshoot; publishers may continue through active phases; pre-existing open upvalues can enter pending after close without fresh allocation. Stopped-GC control below proves at least the first case with the unmodified runtime. A bounded redesign must retain an exact detached suffix, its lifetime and close veto across returns, not simply stop walking and drop the suffix.
- Ownership flush is needed at more boundaries than cycle-start roots: src/lj_gc2.c:8173 flushes before clearing stale uncounted NEEDSCAN at start; :9619 before the global root snapshot; src/lj_gc.c:2046 flushes at the end of sweep's ownership cursor and restarts the cursor if roots/hint remain. Shutdown and FINREG consumers flush too. A new root-work budget must cover these consumers and the ordinary/chain/after-main/VM publishers, including existing-object requeues.

Recovery and physical progress obligations are independent of a zero pending hint

- Queue pressure is represented without allocation: src/lj_gc2.c:14536 publishes to SSB or exact recovery; :14635 publishes worker grey or recovery. The small lane reserves recovery_items before it claims the allocation or publishes PENDING (:10423); CLAIMED/REDIRTY preserve a second pass. src/lj_gc2.c:10617-10644 separates exact outstanding work from sticky recovery_failed, which pins NO_RECLAIM. Absence of pending ownership roots is not absence of semantic SSB/recovery work.
- MARK->WEAK (:4440), WEAK->SWEEP (:4509), weak clearing (:11903), physical SWEEP work (:22208), and SWEEP->IDLE (:6445/:6468) all reject outstanding recovery; no zero-progress drain is an emptiness proof. Worker scheduling and interpreter automatic steps must continue to replay these identities. A policy based only on pending roots could starve rootless semantic work or postpone reclaim indefinitely.
- Rootless closure pairs remain real physical allocations. src/lj_func.c:609 admits them only in the sole-main-TG/internal allocator/no-worker/no-attaching-mutator window and with black allocation when marking is active. :628/:647 commit typed ownership while root stays NONE; :744/:789-820 publish complete bodies and child/proto/environment barriers, charge both total and local allocation, and hand back a rooted result. src/lj_gc.c:2490 and ordinary post-grace typed destruction still require the exact destructor/lifetime/reader proofs. Zero new pending roots therefore shows the bridge charge is a poor proxy, not that collection is unnecessary.
- Every physical free/reuse still requires existing mark, root, recovery, descriptor, counted-reader and grace authority. No predicate above compares an allocation's age with 384 KiB. This audit found no current memory-safety or stalled-recovery defect attributable to that numeric cap. It did not prove correctness for altered pacing, preempted owners, OOM, or MT schedules.

Functional counter evidence

Concrete next step and acceptance boundary

First measure work at the existing cap with temporary, narrowly scoped instrumentation: pending nodes visited/spliced and time in flush/repair; root-snapshot/table slot work; cycle starts; grey/SSB/recovery work; active phase residence and native gate exits; logical bytes plus both reclaimed queues/retired blocks. Instrumentation must be owner/token-local or atomic scalar telemetry, never remote allocator traversal. Before/after root count alone cannot identify every expensive root snapshot, and a stopped-GC speed comparison cannot establish essential collection work.

Then, if the source owner chooses a pacing experiment, freeze the now-integrated runtime and compare 384 versus 512 KiB maximum in isolated trees. Keep hard bytes derived from the *old* capped trigger, the 512-KiB post-hard batch, 32-KiB accounting flush, 4-KiB active step, phase/recovery/read/grace checks and explicit-API behavior unchanged. This one-factor diagnostic tests whether delaying only cycle starts lowers whole-live-graph rescans without weakening the present active collector schedule. A separate conventional 512/1024-KiB trigger/hard variant is useful only to attribute any hard-cadence interaction; it is not the first candidate. Low-heap behavior should be identical whenever the old pause-derived trigger is below 384 KiB.

Use GC-enabled rootless primitive and GC-valued upvalues, retained closures, generic multi-upvalue/C closures (pending-heavy), allocation without pending ownership (strings/cdata/large raw vectors), after-main finalizers, and the current state-churn/insertion-prefix workloads. Repeat enough automatic-only chunks to expose a sawtooth plateau in allocated/retained capacity; capture peaks as well as settled values, finalizer/weak effects, and recovery item ages. Include zero-worker plus configured-worker/secondary-owner modes because rootless admission and collector driving differ. Keep the exact pending-root race, failed queue-growth recovery/REDIRTY, held-reader/late/adoption controls, interpreter and JIT hard-check tests, MARK/SWEEP cooperative progress, recursive FFI collection and explicit stop/restart/step behavior. Current coverage locations include tests/t-gc-root-pending{,-race}.c; t-gc2-recovery.c; t-gc2-{interp,jit}-hard-check.c; t-gc2-jit-{mark,sweep}-coop.c; t-jit-fnew-bump.c; t-arena-empty-reclaimed{,-runtime}.c; tests/suites/m9_m10_gc.lua:118. Some historical broad worker-count expectations predate later traversal repairs; a failure must be attributed against the exact control, not relaxed blindly.

The allocation-account fixture at tests/t-gc2-alloc-account.c:602/:618 encodes hard=2*trigger, so a deliberately decoupled experimental binary will violate that representation assertion. Preserve the exact failure as a known experimental contract delta and verify the actual independent hard schedule; do not weaken the shared test or claim its full suite passed unchanged.

Only if this experiment demonstrates fewer scans with preserved automatic memory/recovery/native-exit progress should a production pacing design proceed. The scalable structural direction remains separate bounded pending-publication work and allocation/reclaim pressure, plus resumable slot/byte traversal. A Boolean pending hint, zero pending-flushed delta, live_cells hint, or an increased arbitrary cap alone supplies none of that authority.
