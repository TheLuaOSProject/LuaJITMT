# b1.2.0 x64 traced-FNEW mcode limit splits (2026-07-13)

The x64 numeric-closure arena fast path emits complete lifetime/root claim,
rollback, recovery-repair, and publication arms. Two helpers had grown beyond
LuaJIT's 128-byte sparse mcode-limit red zone between `checkmclim()` calls:

- `asm_fnew1num_construct_commit()` emitted 737 bytes in the observed trace;
- `asm_fnew1num_construct_pair_claim()` and its nested claim transactions
  exposed a second 854-byte unchecked segment after the first was split.

This was reproducible on the preceding committed revision, including in the
stock assertion suite; it was not caused by cooperative MARK. Release builds
usually had enough room and therefore hid the missing proof, but the assertion
correctly demonstrated that an unlucky near-page trace could cross the real
lower mcode limit before the next sparse check.

The repair leaves `MCLIM_REDZONE` and every assertion unchanged. It inserts
code-generation-time `checkmclim()` boundaries between each complete
retry/repair arm, packed lifetime/root transaction, and nested pair-claim
transaction. These checks emit no trace instructions and add no runtime fast
path cost; they only let the assembler acquire another mcode area before
starting a segment which cannot fit in the current reserve.

Validation:

- focused O2 assertion hard-check: 20/20;
- assertion build with `LUAJIT_RANDOM_RA`: hard-check 50/50;
- `t-jit-fnew-bump`, both default and `LJ_TEST_TRACED_FNEW=1`;
- the integrated `m3_gc2_paranoia` suite, including 509 stock JIT tests and
  387 stock no-JIT tests;
- `git diff --check`.
