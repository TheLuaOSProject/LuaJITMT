SIMD programming in LuaJIT is ordinary Lua code operating on FFI vector cdata. A vector type is declared with the standard GCC vector attribute: 

local ffi = require("ffi")
ffi.cdef[[
typedef float   float4 __attribute__((vector_size(16)));
typedef int32_t int4   __attribute__((vector_size(16)));
]]
local float4 = ffi.typeof("float4")

local a = float4(1, 2, 3, 4)   -- one value per lane
local b = float4(2)            -- splat to every lane
local c = a * b + 1            -- packed multiply-add, scalar splatted
print(c[0], c[3])              --> 3  9

Hot loops over vector cdata compile to real packed x86-64 SSE instructions. The ffi.simd module adds only the operations that Lua operators cannot express.

Operators on vector cdata

Both operands must be vectors of exactly the same type, or one operand may be a number (or a scalar cdata) which is converted with the ordinary FFI conversion rules and splatted across all lanes. The result has the vector operand's type.

a + blane-wise add; integer lanes wrap around
a - blane-wise subtract
a * blane-wise multiply, low half of the product
a / blane-wise divide, floating-point vectors only
-alane-wise negate
a == bwhole-vector equality, returns a boolean
v[i]read lane i
v[i] = xan error: vector lanes are immutable, use simd.insert()

a < b, a <= b, a % b, a ^ b, #a and a .. b raise an error: a single boolean or a scalar is not a useful answer for a vector. Use simd.lt() and friends, which return a mask.

== compares lane by lane, so a NaN lane is never equal and +0 equals -0. Comparing a vector with anything that is not a convertible scalar or a vector of the same type is simply false, never an error.

Supported vector types

A vector type is supported when its element is a plain number type of 1, 2, 4 or 8 bytes and it has at least two lanes. The interpreter supports every such type at any power-of-two width. The JIT has a complete 128-bit backend and, on AVX2 machines, a broad 256-bit backend. Other widths and operations outside the current 256-bit subset keep working but stay interpreted.

Masks produced by the comparison functions are signed integer vectors with the same lane width and lane count as their inputs, with all bits set for true and all bits clear for false.

Module functions

local simd = require("ffi.simd")

Every binary function accepts a matching vector or a splattable scalar as its second operand.

Bitwise

simd.band(a, b)a & b
simd.bor(a, b)a | b
simd.bxor(a, b)a ^ b
simd.bandn(a, b)~a & b
simd.bnot(a)~a

These work on any vector, including floating-point ones, which is how masks are combined. 

local mask = simd.lt(v, float4(0))
local negatives = simd.band(v, mask)

Shifts

simd.shl(a, n)shift each lane left
simd.shr(a, n)logical shift right
simd.sar(a, n)arithmetic shift right

Integer vectors only. The count is treated as unsigned: a count of at least the lane width gives zero for shl/shr and a full sign fill for sar, matching the x86 packed shifts.

The count may be a constant or a value computed at runtime; both compile to packed code. 8-bit lanes and the 64-bit sar have no x86 instruction and are rewritten into a wider shift plus a mask, which costs a few extra instructions when the count is not a constant.

The count may instead be a vector with the same lane width and lane count, in which case each lane shifts by its own amount. The same unsigned out-of-range rule applies per lane. This compiles to the AVX2 per-lane shifts on every integer lane width. AVX2 has no byte or word form, so 8- and 16-bit lanes are split into dword pieces, shifted independently, and recombined in packed code. 

local v = simd.shl(x, int4(0, 1, 2, 3))   -- each lane shifts differently

Comparisons and masks

simd.eq(a, b), simd.ne(a, b)lane-wise equality mask
simd.lt, simd.le, simd.gt, simd.gelane-wise ordering mask
simd.select(m, a, b)per lane: m set takes a, else b
simd.movemask(v)bit i is the sign bit of lane i
simd.allof(v), simd.anyof(v)all / any lane sign bit set

Floating-point ne is unordered (true if either side is NaN); the other five are ordered.

simd.mulhi() is integer only and takes its signedness from the lane type. It is the other half of the same multiply the * operator performs. Together the two halves let fixed-point code select any result scaling without losing the carry between them. For example, a signed Q15 multiply shifts the full product right by 15: 

local q15  = int16x8(math.floor(0.6 * 32768 + 0.5))
local lo   = samples * q15
local hi   = simd.mulhi(samples, q15)
local out  = simd.bor(simd.shl(hi, 1), simd.shr(lo, 15))

simd.fma(a, b, c) computes a*b + c with a single rounding, which is not the same value as the two-step a*b + c. It is the IEEE 754 fused multiply-add, so simd.fma(a, b, -(a*b)) is exactly the rounding error of the product. The interpreter and the JIT agree bit for bit; on a CPU without FMA the operation stays interpreted rather than silently rounding differently. 

-- Branchless clamp.
local function clamp(v, lo, hi) return simd.min(simd.max(v, lo), hi) end

-- Early out when no lane matches.
if simd.anyof(simd.gt(v, limit)) then ... end

Arithmetic that has no operator

simd.min(a, b)per lane a < b and a or b
simd.max(a, b)per lane a > b and a or b
simd.mulhi(a, b)high half of the lane product; a*b is the low half
simd.abs(a)absolute value; wraps for the most negative signed lane
simd.sqrt(a)square root, floating-point only
simd.fma(a, b, c)a*b + c with a single rounding, floating-point only
simd.floor/ceil/trunc/round(a)rounding, floating-point only; round is ties-to-even; a NaN operand comes back quieted
simd.adds(a, b), simd.subs(a, b)saturating add/subtract, 8 and 16 bit lanes only

min and max follow the x86 instructions exactly: for floating-point lanes a NaN in either operand yields the second operand, and min(+0, -0) is -0.

Horizontal reductions

simd.hsum(v)sum of all lanes
simd.hmin(v), simd.hmax(v)smallest / largest lane

The result is a single value of the element type. Reductions combine lanes with a fixed pairwise halving tree, not left to right, so the answer does not depend on whether the code is interpreted or compiled — which matters for float addition and for the asymmetric NaN behaviour of min/max. 

local acc = float4(0)
for i = 0, n-1 do local v = p[i]; acc = acc + v * v end
local dot = simd.hsum(acc)

Lanes and shuffles

simd.insert(v, i, x)copy of v with lane i replaced by x
simd.shuffle(v, i0, ...)permute lanes of v; one index per lane
simd.shuffle(v, idxvec)permute lanes of v by a run-time index vector
simd.shuffle2(a, b, i0, ...)permute the concatenation of a and b

Indices are lane numbers. For shuffle2, indices below the lane count select from a and the rest from b. Reading a lane uses ordinary indexing (v[i]).

Given a single vector second argument instead of a list of numbers, simd.shuffle() takes one index per lane from it at run time. The index vector must be an integer vector with the same lane width and lane count as v. Each index is reduced modulo the lane count, so any value — negative or out of range — still selects a lane and the operation never raises. This compiles to PSHUFB, one instruction for a byte vector. 

local rev  = simd.shuffle(v, 3, 2, 1, 0)          -- reverse
local zip  = simd.shuffle2(a, b, 0, 4, 1, 5)      -- interleave low halves
local tbl  = simd.shuffle(v, idx)                 -- idx chosen at run time
local one  = simd.insert(v, 2, 42)                -- v with lane 2 set to 42

Conversions

simd.bitcast(ct, v)reinterpret the bits as vector type ct
simd.convert(ct, v)numeric lane conversion to ct

bitcast requires equal total size and changes no bits. convert requires an equal lane count. ct is a ctype from ffi.typeof(). Integer to integer sign- or zero-extends or truncates. Floating-point to integer truncates toward zero and yields the integer indefinite value — the minimum signed value of the destination width — for a NaN or for anything outside the destination's signed range, which is what the packed conversion instructions do. 

local bits = simd.bitcast(int4, v)                -- raw bit pattern
local ints = simd.convert(int4, v)                -- 1.9 -> 1, -1.9 -> -1

Introspection

simd.isvector(x)is this a supported vector cdata or ctype?
simd.lanes(x)number of lanes
simd.elementtype(x)ctype of one lane
simd.features()table of detected CPU features and vecsize

features().vecsize is the vector width in bytes that the JIT compiles natively: 32 with AVX2, 16 with SSE2, or 0 if this build has no vector backend.

Loading and storing

No special functions are needed: cast a pointer to a vector pointer and dereference it. All vector loads and stores use unaligned instructions, so the address does not have to be aligned to the 16- or 32-byte vector width. 

local buf = ffi.new("float[?]", n)
local vp  = ffi.cast(ffi.typeof("$ *", float4), buf)
for i = 0, n/4 - 1 do vp[i] = vp[i] * float4(2) end

Notes and limits

  • Vector lanes are immutable, which is what lets the compiler keep a vector in a register. Build a new vector with simd.insert() instead.
  • The supported target is x86-64-v3. CPU features are still detected at run time, so the same binary works on older machines: an operation without a packed instruction is never scalarised, the trace is abandoned and the code keeps running interpreted with identical results. simd.features() reports what was found.
  • The 256-bit JIT supports the ordinary vector operators, dynamic scalar splats, comparisons and masks, min/max, shifts, abs/sqrt/rounding, FMA, saturating arithmetic, mulhi at every integer lane width, direct 32-bit conversions, logical/select/bitcast, unaligned loads and stores, horizontal reductions, constant and runtime-index shuffles, two-source shuffles, and constant or runtime-index insertion.
  • When AVX is present every packed instruction is emitted in its three operand VEX form.
  • An ordinary a*b + c written with operators is never contracted into a fused multiply-add: that would round once where the interpreter rounds twice. Ask for the fused form explicitly with simd.fma(), which rounds once in both the interpreter and the JIT.
  • Vectors can be passed to and returned from C functions by value. On x86-64 SysV this also works for FFI callbacks: a Lua function cast to a C function pointer may take and return 8 or 16 byte vectors by value, in registers or on the stack, mixed freely with ordinary arguments. On Windows x64, on x86, and for 32-byte or wider vectors, such a cast is still rejected with a “cannot convert” error — pass a pointer instead.
